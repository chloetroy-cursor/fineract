= Observability overhead on loan read and repayment

This section reports what the loan lifecycle and Loan COB instrumentation costs on two API calls: reading a loan and posting a repayment. It was measured on 12 November 2026 with https://github.com/mcollina/autocannon[autocannon] against images built by Gradle from the two source trees. The scripts are in `.cursor/skills/verify-fineract/bench/`. The numbers of every run are in `bench/results/2026-11-12-runs.jsonl`, and `bench/analyze.py` prints every table of this section from that file.

== Result

No overhead was found. For both workloads, with JSON logs off and with JSON logs on, every difference from Before in throughput, in p50, p97.5 and p99 latency and in server CPU per request is inside the noise. The 95% intervals put the cost at no more than 2.6% of throughput for the loan read and 1.7% for the repayment. A smaller cost may exist; this setup cannot see it.

== Method

=== Machine and versions

One cloud VM ran the server, MySQL and autocannon: 8 vCPU (Intel Xeon, family 6 model 207, KVM), 47 GiB RAM, Ubuntu 24.04.5, kernel 6.12.113. Docker 29.9.3 with the `fuse-overlayfs` storage driver, Docker Compose 5.7.1, MySQL 8.4.13 (`mysql:8`), Node.js 22.23.4, autocannon 9.0.0. The images run on Azul Zulu 25.0.5 and were built with Temurin 25.0.5 and Gradle 9.7.1.

=== Settings, the same for every variant

* The `verify-fineract` stack with `FINERACT_DB=mysql`: `docker-compose-mysql-test.yml` plus `compose/fineract-demo.yml`, which turns on `percentiles-histogram` for `http.server.requests`. MySQL runs with its image defaults, including `innodb_flush_log_at_trx_commit=1` and `sync_binlog=1`.
* `bench/bench-compose.yml` on top, with two changes:
** `FINERACT_SERVER_TOMCAT_MAX_KEEP_ALIVE_REQUESTS=-1`. With the default of 100 Tomcat closes each connection after 100 requests. autocannon then reconnects and pairs every later response on that connection with an older request, so its latencies grow with every reconnect. In a trial with the default it reported a mean of 60 ms at 430 requests a second on 8 connections, which cannot both be true.
** `JAVA_TOOL_OPTIONS` as in `config/docker/env/fineract-common.env` with three changes: `-Xms4G -Xmx4G` instead of `-Xmx1G`, no `-XX:TieredStopAtLevel=1`, no JDWP agent. <<observability-overhead-heap>> gives the reason.
* autocannon: 8 connections, 30 seconds for a measured run, no pipelining, 30 second timeout.
* The scheduler was left on, as shipped. No Prometheus server scraped the application during the runs.

=== Data

`fineract seed-loans 5000` created 5,000 loans with the `seed-loan` terms on the Before server: 12,000 over 12 monthly repayments at 1% flat a month, disbursed 01 January 2026. The server and MySQL were then stopped and the MySQL data directory was archived. Before every server start the script restores that archive and checks its SHA-256, so every start of every variant begins from the same bytes. The loans are split into five pools of 1,000:

[cols="1,4"]
|===
|Loans |Use

|1 to 1,000
|Repayments during warm-up

|1,001 to 2,000
|Every read, in warm-up and in measured runs. These loans are never repaid.

|2,001 to 5,000
|One pool for each of the three measured repayment runs of a start, so every measured repayment run starts on loans without a repayment. A run posts 6 to 8 repayments of 10 to each loan, against 13,440 outstanding.
|===

=== Runs

One cycle starts each variant once, in an order that rotates from cycle to cycle. After each start:

. Warm-up: 90 seconds of reads, then 60 seconds of repayments, at the same 8 connections.
. Three times: a 30 second read run, then a 30 second repayment run.

Ten cycles were run, from 02:28 to 05:55 UTC: 10 starts of each variant, and 30 measured runs of each workload for each variant.

Six cycles were planned. After six, the repayment p97.5 of After with JSON logs off stood 3.7% above Before with an interval of +0.8% to +6.4%, and three other cells said that After was faster, which added instrumentation cannot cause. Four cycles were added to settle it. All ten are reported, and with ten no cell is outside the noise.

=== Checks on every run

The script stops the benchmark if a run fails any of these. None did.

* Every response has a 2xx status, and autocannon reports no error and no timeout. The 240 runs, warm-ups included, returned 5,896,732 responses, all with status 200.
* For repayments, a second read-only view: `summary.totalRepayment` of 25 loans of the pool is read before and after the run and must have grown by 10 for every request sent to that loan. One request per loan may be missing, because autocannon drops the requests in flight when the run ends.

=== Numbers

* Throughput is autocannon's `requests.average`.
* p50, p97.5 and p99 are computed from the response time autocannon reports for each 2xx response. autocannon's own percentiles are rounded down to whole milliseconds, which is 12% of the read median.
* Server CPU is the CPU time of the Fineract container (`cpu.stat` of its cgroup) during the run, divided by the number of responses. It includes garbage collection and JIT threads.
* A variant's value is the median over all its measured runs. Overhead is the difference between the After median and the Before median as a percentage of Before, signed so that positive is worse: lower throughput, higher latency, more CPU.
* The 95% interval is a bootstrap over cycles: cycles are drawn with replacement 10,000 times and the overhead is recomputed from the runs of the drawn cycles. Runs inside one JVM share its JIT and GC state, so they are not treated as independent.
* A/A is the same overhead computed between the odd and the even cycles of Before, where nothing changed.
* A difference is called outside the noise only when its interval excludes zero and it is larger than the A/A difference.

[[observability-overhead-noise]]
== Noise

* Run to run, inside one start: half the interquartile range of Before is ±1.1% of the read throughput and ±0.8% of the repayment throughput. For p97.5 it is ±1.8% and ±3.8%.
* Start to start: the per-start medians of Before's throughput span ±3.7% for reads and ±2.0% for repayments, with no change of code or data. For the repayment p97.5 they span ±7.8%. This is the noise that limits the benchmark, and the reason the statistics treat a start as the unit.
* Inside single cycles the read throughput overhead of After ranged from -3.9% to +6.2%, with After the worse one in 5 of 10. One cycle, or the first cycle alone, can show anything in that range.
* The A/A column is one split of ten starts and can be small by luck: 0.1% for the repayment p50. Read it together with the start spread.
* Every interval in the tables contains zero. The widest reach is +2.7% for throughput and p50, +3.5% for the read tail, +4.3% for the repayment tail and +3.1% for server CPU. Differences below those values are inside the noise of this setup.
* One difference between starts remains unexplained. In 22 of the 30 starts G1 made 4 concurrent-cycle pauses; in 8 it made 22 to 30, and those starts used 2% more server CPU per read. Four of the 8 were Before, four were After with JSON logs off, none was After with JSON logs on. That may be why JSON logs on looks slightly faster than JSON logs off. The cause was not investigated.

== Reasons to distrust these numbers

* The resolution is a few percent. An overhead below about 2% of throughput, or below about 4% of tail latency, would not have been detected.
* The server, MySQL and autocannon shared one 8 vCPU cloud VM, without CPU pinning, and 8 connections keep it close to saturated: the server used about 4 cores and MySQL 2.5 to 3.5. The absolute figures are not capacity figures, and other tenants of the host can move them.
* The JVM flags are not the flags of the `verify-fineract` stack: 4 GiB heap instead of 1 GiB, C2 enabled, no debugger agent. Nothing was measured with the stock flags, where a C1-only JIT could make the same instrumentation relatively cheaper or dearer.
* The load is closed-loop: a connection sends its next request when the previous one returns. Latency therefore follows throughput, and the percentiles are not corrected for coordinated omission. No run at a fixed request rate below saturation was made.
* Histogram buckets for `http.server.requests` are on in every variant, because the stack turns them on. With them off every variant does less work per request, and the relative overhead was not measured.
* Nothing scraped `/actuator/prometheus` during the runs. One scrape after the runs took about 0.12 s in every variant and returned 181 to 190 KB for Before and 188 to 197 KB for After.
* JSON logs were measured at the default log level, where these requests log nothing. At `DEBUG`, where every request logs, the cost of JSON formatting is not known from this report.
* The COB step timer and the loans-processed counter are not on the path of either request. This report says nothing about their cost during Loan COB.
* The workloads are narrow: one tenant, one flat-interest product, loans with at most 8 repayments, reads and repayments never mixed in one run, 8 connections.
* Keep-alive was unlimited. A client that reconnects every 100 requests pays a TLS handshake that these numbers leave out, in every variant.
* After is a local merge of the four branches as they were on 12 November 2026, built with tests skipped. It is not the commit that will exist on `addepar-demo` once they are merged.
* The sample size was extended from six to ten cycles after looking at the first six. Nothing was dropped, but the stopping point was not fixed in advance.
* The interval is a bootstrap over ten cycles, which tends to be too narrow for so few units.

== How to rerun

The build needs JDK 25 and Docker. `before` and `after` are any two checkouts; `after` here was `addepar-demo` with the four branches merged.

[source,bash]
----
# in the Before checkout, then in the After checkout
FINERACT_IMAGE=fineract:before .cursor/skills/verify-fineract/scripts/fineract build
FINERACT_IMAGE=fineract:after  .cursor/skills/verify-fineract/scripts/fineract build

# seed once on the Before image and snapshot the database
FINERACT_DB=mysql FINERACT_IMAGE=fineract:before .cursor/skills/verify-fineract/scripts/fineract up
.cursor/skills/verify-fineract/bench/overhead.sh install
.cursor/skills/verify-fineract/bench/overhead.sh seed

# measure, then summarise
JVM=bench CYCLES=6 .cursor/skills/verify-fineract/bench/overhead.sh run
